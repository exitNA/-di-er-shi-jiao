# 第二视角 MVP 交付策略设计

## 1. 目标

本设计把已确认的 [`docs/product-design.md`](../../product-design.md) 转换为可实施的工程路线：

1. 用一张总路线图说明完整 MVP 的阶段、依赖、交付结果和验收门槛；
2. 把第一阶段限定为一个可独立验证的真实纵向闭环；
3. 为后续 `writing-plans` 提供足够明确的架构、边界、数据流、恢复策略和测试策略；
4. 将供应商、部署平台和交付节奏等待决策项集中记录，不让它们改变产品领域边界。

本文不替代产品设计。功能范围、领域术语、产品指标和验收场景仍以 `docs/product-design.md`、`CONTEXT.md` 和 ADR-0001 为准。

## 2. 当前基线

仓库当前已经具备：

- Next.js 16、React 19、TypeScript 和 Tailwind CSS 的生产基线；
- App Router 的根布局、首页和错误回退；
- `lint`、`typecheck` 和 `build` 脚本；
- 已确认的产品设计、领域术语与“单一前台 Agent 协调内部专家 Agent”架构决策。

仓库尚未引入认证、数据库、测试框架、模型调用、搜索、后台任务、流式状态、监控和业务功能。

## 3. 交付路径比较

### 3.1 推荐：模块化单体 + 纵向切片

每个阶段交付一条可运行、可测试、可演示的用户路径。Next.js 应用保持单体部署形态，内部按领域模块、应用用例和基础设施适配器划分边界。

优势：

- 第一阶段就验证认证、持久化、Agent、搜索、渐进展示和恢复之间的真实集成；
- 后续对话、画像和删除能力复用同一任务与所有权模型；
- 保持部署简单，同时为模型、搜索和任务运行器预留可替换接口；
- 每个阶段都有用户可见结果和清晰的回归边界。

代价：

- 第一阶段需要同时建立若干基础能力；
- 必须严格限制第一阶段范围，避免把全部 MVP 一次带入。

### 3.2 备选：基础设施分层先行

先完成数据库、认证、队列、可观测性和通用组件，再实现产品路径。

优势是底层能力集中、短期代码组织整齐；代价是较晚才能验证真实 Agent 流程，容易围绕尚未发生的需求建立过度抽象，也无法尽早测量 10 秒首模块和 60 秒 P95。

### 3.3 备选：Agent 原型先行

先用无账号、弱持久化页面验证提示词、专家分工和报告质量，再补齐产品能力。

优势是最快获得模型质量反馈；代价是原型的数据流、流式协议和运行方式通常无法直接演进到可恢复产品，认证、历史、资源归属与删除需要二次改造。

### 3.4 结论

采用“模块化单体 + 纵向切片”。质量实验作为第一阶段内部工作流存在，不单独形成一次性原型；基础设施只在当前纵向切片需要时引入。

## 4. 总体架构

### 4.1 系统形态

系统保持一个 Next.js 全栈代码库，运行时分为三个协作部分：

1. **Web 应用**：页面、Route Handlers、会话校验、用户操作和实时状态订阅；
2. **任务执行器**：运行可重试、可追踪的长耗时分析与后续 Agent 任务；
3. **PostgreSQL**：保存产品事实、任务状态、报告快照、事件、对话、反馈和授权。

任务执行器可以由托管服务或自托管实现，但只通过应用定义的任务端口调用领域用例。页面不直接依赖任务供应商的数据结构。

### 4.2 代码边界

建议采用以下边界：

```text
src/
├── app/                       # 路由、页面、Route Handlers
├── components/                # 跨功能展示组件
├── features/
│   ├── auth/                  # 登录交互和会话入口
│   ├── analysis/              # 输入、分析任务、报告、历史
│   ├── conversation/          # 质疑、消息、修订
│   ├── thinking/              # 思考问题、回应、本次反馈
│   ├── profile/               # 长期画像、授权、证据范围
│   └── data-control/          # 删除与重新计算
├── server/
│   ├── application/           # 用例与事务边界
│   ├── domain/                # 领域状态、规则、结构化契约
│   ├── agents/                # 前台 Agent、专家和提示配置
│   ├── ports/                 # 模型、搜索、任务、时钟等端口
│   └── adapters/              # PostgreSQL 与外部供应商适配器
└── lib/                       # 无领域含义的共享工具
```

`app/` 只负责协议转换和 UI 组合；业务状态转换由 `server/application` 和 `server/domain` 完成。供应商 SDK 限制在 `server/adapters`，防止模型、搜索或后台任务选择渗入产品内核。

### 4.3 Agent 编排

前台“第二视角 Agent”对用户保持唯一角色，内部使用固定专家。为同时满足自主性和可恢复性，编排采用“确定性工作流外壳 + Agent 决策内核”：

1. 应用层创建分析任务并固定配置版本；
2. 前台 Agent 识别素材类型和分析目标；
3. 应用层保证论证分析、信源研究、多视角挑战和风险审查四个专家均被调用；
4. 无依赖的专家并行执行，各自在独立上下文中返回结构化结果；
5. 前台 Agent 综合草稿；
6. 多视角挑战专家执行二次审校；
7. 应用层校验最低报告结构、溯源字段和状态转换后发布基线报告。

Agent 可以决定分析顺序、工具参数、补充检索和表达方式；应用层固定必调专家、结构化输出、次数上限、超时、重试、安全与权限规则。这一边界延续 ADR-0001，并使单个模块能够恢复。

推荐默认使用 AI SDK 的 `ToolLoopAgent`、结构化输出和 `@ai-sdk/openai-compatible` 适配器；专家作为受限工具暴露给前台 Agent。LLM 端点、API Key 和模型 ID 由服务端环境变量配置，不进入浏览器。所有 Agent 输入输出使用 Zod 契约验证，原始模型响应不直接进入页面或数据库的发布字段。

### 4.4 数据模型原则

第一阶段建立能够向完整 MVP 演进的最小表集合：

- `users`、`password_credentials`、`sessions`：用户、密码哈希与可撤销会话；
- `analysis_materials`：原始文本、语言和内容摘要；
- `analysis_jobs`：任务状态、配置版本、开始/结束时间和恢复信息；
- `expert_runs`：专家类型、状态、尝试次数、耗时和受保护的运行元数据；
- `reports`：基线版本与当前版本；
- `report_modules`：速览和五个固定模块的结构化快照及独立状态；
- `report_sources`：来源元数据与证据关系；
- `analysis_events`：供渐进展示、恢复和埋点消费的追加事件。

后续阶段按首次需要加入 `messages`、`report_revisions`、`thought_responses`、`profile_feedback`、`profile_evidence`、`thinking_profiles` 和 `profile_consents`。

所有用户资源包含不可为空的所有者标识。所有读取、修改和删除用例同时校验会话与资源归属，不把前端传入的用户 ID 当作授权依据。

### 4.5 渐进展示与恢复

渐进展示以数据库中的任务与模块状态为事实来源：

- 任务执行器完成或更新模块时，在同一事务中保存模块快照和事件；
- Web 端通过服务端事件流订阅任务事件；
- 断线重连携带最后事件游标，服务端补发缺失事件；
- 页面刷新先读取当前快照，再继续订阅；
- 实时通道不可用时，客户端退化为带退避的状态轮询；
- 任务执行器重试时复用同一分析任务和已完成模块，不创建重复报告。

流不承担唯一持久化责任，因此连接中断不会丢失已完成内容。

## 5. 第一阶段：真实基线报告闭环

### 5.1 阶段目标

交付以下端到端路径：

`用户名密码注册或登录 → 提交文本 → 查看渐进式真实基线报告 → 刷新后恢复 → 从历史重新打开`

这一阶段验证产品最核心、技术风险最高的“认知体检”能力，同时为后续对话和画像提供稳定的用户、任务、报告和事件主干。

### 5.2 必须交付

#### 工程基线

- Vitest、React Testing Library、`@testing-library/jest-dom` 和 Playwright；
- 测试数据库、迁移、种子与清理机制；
- 类型安全环境变量校验；
- 统一错误分类、结构化日志和任务级追踪；
- 模型、搜索、任务执行器和时钟端口；
- 开发环境的确定性假实现，保证无外部密钥也能运行自动测试。

#### 认证

- 用户名、密码注册、登录、退出和受保护路由；
- 用户名规范化后保持唯一，登录匹配不区分大小写；
- 密码允许长密码、Unicode 和空格，不设置字符种类组合规则；
- 密码使用 Argon2id 和每条凭据的独立盐进行自适应哈希，绝不保存或记录明文；
- 登录失败使用统一响应，避免泄露账号是否存在；
- 注册与登录按 IP 和规范化用户名限制频率；
- 登录成功后创建高熵随机会话，数据库只保存会话令牌哈希；
- 会话通过 `HttpOnly`、`Secure`、`SameSite` Cookie 传递，支持空闲过期、绝对过期和退出撤销；
- 状态修改请求校验来源并具备 CSRF 防护；
- 会话与数据库用户建立稳定映射。

认证由应用内独立模块实现，不依赖邮箱或第三方身份服务。密码哈希使用成熟的 Argon2id 实现，会话作为服务器端不透明凭据管理。

#### 输入与任务

- 1–20,000 字符文本输入；
- 中文、英文和中英混合输入，输出固定为简体中文；
- 空输入、长度、内容安全和重复提交保护；
- 成功提交后原子创建分析素材与分析任务；
- 用户只能读取自己的任务。

普通文章 URL 和公众号链接不进入第一阶段。

#### 基线报告

- 前台 Agent 和四类必调专家真实运行；
- 速览、论证骨架、多视角地图、信源对照、认知风险和思考对话六个区域；
- 每个关键表述包含类型、定位或来源、置信度；
- 信源对照目标使用 3–5 个独立高质量信源；
- 多视角挑战专家对综合草稿执行二次审校；
- 事实型素材按产品设计中的替代路径呈现；
- 报告和 Agent 配置保存版本号。

“思考对话”在第一阶段只展示 Agent 当前最值得追问的问题，不接受回应，也不生成五维反馈。

#### 工作区与历史

- 模块状态和已经完成的内容渐进展示；
- 处理中、部分完成、已完成和待恢复状态；
- 刷新或重连后恢复报告；
- 信源失败时继续展示内容分析，并提供信源模块重试；
- 历史列表、报告详情和继续查看；
- 报告 AI 提示、来源域名、置信度和不确定性可见；
- 键盘可操作，流式更新不抢夺焦点，并提供辅助技术状态提示。

#### 质量与指标

- 记录 `analysis_submitted`、`first_module_shown`、`baseline_report_completed` 和 `report_degraded`；
- 记录首模块耗时、完整报告耗时、各专家成功率与耗时、模型/搜索成本；
- 建立 30 条固定样本的数据格式、评审脚本和初始样本集；
- 阶段退出前满足报告结构、引用有效性、证据匹配、风险准确性和中立性门槛；
- 测量首个可用模块 10 秒目标和完整报告 P95 60 秒目标。

### 5.3 第一阶段暂不交付

- 针对报告的持续对话和报告修订；
- 思考回应有效性判断与本次五维反馈；
- 长期思维画像、画像授权和证据范围管理；
- 单份历史删除、画像重算和账号级联删除；
- 普通文章或公众号 URL 解析；
- 分享、文件、音视频、移动端和多模型交叉验证。

这些能力均保留在总路线图中，不影响第一阶段数据模型向前兼容。

### 5.4 第一阶段完成标准

第一阶段只有在以下条件同时满足时完成：

1. 新用户可使用用户名和密码注册、登录并退出；
2. 可提交合法文本并生成真实基线报告；
3. 四个必调专家均有独立运行记录；
4. 报告包含速览和五个固定模块，失败模块清楚降级；
5. 刷新、断线和单专家重试不丢失已完成模块；
6. 用户只能访问自己的任务和报告；
7. 历史列表能够重新打开已完成或待恢复报告；
8. 单元、组件、集成和关键 Playwright 路径通过；
9. 30 条固定样本达到产品设计的质量门槛；
10. `lint`、`typecheck`、测试和生产构建全部通过。

## 6. 完整 MVP 路线图

后续 `writing-plans` 生成的第一份详细实施计划覆盖 M0 与 M1。M0 是 M1 的起始任务组，不作为独立产品发布；完成二者才算交付第 5 节定义的第一阶段。

### M0：工程与质量主干

建立测试、环境配置、PostgreSQL、迁移、端口/适配器、错误分类、日志和评估样本格式。M0 只实现 M1 需要的基础，不建设通用平台。

### M1：真实基线报告闭环

完成第 5 节定义的第一阶段。它是所有后续阶段的共同依赖。

### M2：边聊边拆与报告修订

在 M1 的报告之上增加：

- 针对具体报告条目的质疑入口；
- 消息历史与连续上下文；
- 按问题调用相关专家或搜索工具；
- 报告修订、变化位置、理由、新证据和简明修订记录；
- 对话与修订的断线恢复；
- `report_item_challenged` 和 `report_revised` 埋点。

退出条件对应产品验收场景 C。

### M3：思考回应与本次五维反馈

增加：

- Agent 思考问题、用户回应和后续追问；
- 有效思考回应的语义判定；
- 五维固定量规、本次反馈、证据片段和置信度；
- 无画像授权时仍可查看本次反馈；
- 有效思考闭环指标；
- `thought_response_submitted`、`thought_response_accepted` 和 `profile_feedback_viewed`。

M3 完成后，产品首次形成完整北极星闭环。

### M4：长期画像、授权与数据控制

增加：

- 独立画像授权、撤回和纳入范围调整；
- 3 份报告且 5 次有效回应的冷启动门槛；
- 画像证据、五维趋势与置信度重算；
- 高意图辅助行为；
- 单份历史删除、清空画像和删除账号数据；
- 级联删除、审计结果和失败恢复。

退出条件覆盖产品验收场景 E、F，并通过跨用户隔离和删除一致性测试。

### M5：可选链接输入

在文本闭环稳定后，按投入产出选择：

- 普通文章 URL 解析；
- 公众号文章解析；
- 提取摘要确认；
- 解析失败时无缝切换到粘贴正文。

M5 是可选增强，不阻塞 MVP 最小闭环和北极星指标验证。

### M6：发布验证与运行加固

- 全量 30 条固定样本复评；
- 20 名目标用户可用性验证；
- 性能、可靠性、安全和可访问性验收；
- 仪表盘、告警、成本预算与配置回退演练；
- 数据备份、迁移和删除演练；
- 目标平台部署适配；
- 功能冻结后只处理阻断问题和质量回退。

## 7. 依赖与并行关系

```text
M0 → M1 → M2 → M3 → M4 → M6
          └──────────────→ M5（可选，可与 M3/M4 并行）
```

- M2 依赖 M1 的报告、事件和任务恢复；
- M3 依赖 M2 的连续对话，但本次反馈与长期画像分开交付；
- M4 依赖 M3 的有效回应和反馈证据；
- M5 只依赖 M1 的分析素材入口；
- M6 的监控、评估和安全工作从 M0 开始增量建设，最终集中验收。

## 8. 错误处理与连续服务

错误按可恢复性和用户影响分类：

- **输入错误**：不创建任务，返回具体可修正字段；
- **认证错误**：登录使用统一对外信息，内部保留凭据错误、会话失效或频率限制类型；
- **模型结构错误**：在同一专家运行内自动校正一次，仍失败则标记模块可重试；
- **搜索或抓取错误**：信源模块降级，不阻断论证、多视角、风险和思考问题；
- **任务执行中断**：任务进入待恢复，重试从最后稳定模块继续；
- **持久化冲突**：使用幂等键和状态版本阻止重复任务、重复模块和旧结果覆盖新结果；
- **权限错误**：返回资源不可用，不泄露资源是否属于其他用户；
- **未知系统错误**：记录任务 ID、错误类型和安全元数据，页面提供恢复入口。

完整原文、用户名、密码、会话令牌、用户回应和模型敏感输入不写入普通日志。

## 9. 测试与验证策略

### 9.1 测试层次

- **领域单元测试**：状态转换、有效回应规则、画像门槛、来源独立性、风险字段和删除范围；
- **应用集成测试**：使用真实 PostgreSQL 测试事务、所有权、幂等、恢复和级联；
- **Agent 契约测试**：以固定模型响应和搜索结果验证 Zod 契约、重试、降级与提示注入隔离；
- **组件测试**：使用 React Testing Library 断言渐进模块、错误、重试、来源和辅助技术状态；
- **端到端测试**：Playwright 覆盖登录、提交、渐进报告、刷新恢复、对话修订、反馈和删除等关键路径；
- **离线评估**：30 条固定样本由两名评审按产品门槛评价；
- **生产冒烟与监控**：验证真实注册登录、模型、搜索、任务运行和数据库连接。

### 9.2 测试替身

外部服务通过端口替换：

- 单元和大多数集成测试使用确定性模型、搜索和任务替身；
- MSW 只用于浏览器侧或第三方 HTTP 协议测试；
- 少量供应商契约测试在具备密钥时运行；
- 固定时间、随机 ID 和重试退避，保证恢复测试可重复。

### 9.3 阶段门禁

每个里程碑必须：

1. 满足该阶段用户可见验收场景；
2. 不破坏此前里程碑的关键 E2E；
3. 通过 `lint`、`typecheck`、单元/组件/集成测试和生产构建；
4. 更新配置版本、迁移与运行文档；
5. 记录性能、可靠性、成本和降级结果。

## 10. 推荐默认技术选择

这些选择用于让实施计划保持具体，同时通过端口保留替代能力：

| 能力 | 推荐默认值 | 选择理由 |
| --- | --- | --- |
| 应用 | 现有 Next.js App Router | 延续仓库基线 |
| 数据库 | PostgreSQL | 适合关系、事务、所有权和级联删除 |
| ORM/迁移 | Drizzle ORM + 提交 SQL 迁移 | TypeScript 契约清晰，迁移可审查 |
| 认证 | 应用内用户名密码模块 + Argon2id + 数据库会话 | 无邮箱依赖，凭据和会话规则可完整审计 |
| Agent | AI SDK `ToolLoopAgent` + `@ai-sdk/openai-compatible` + Zod | 兼容通用 OpenAI 协议服务并支持结构化 Agent 工作流 |
| 后台任务 | Trigger.dev 适配器 | 支持长任务、重试、队列、实时状态和自托管替代 |
| 实时恢复 | 持久化事件 + SSE，轮询降级 | 断线不丢状态，客户端协议保持简单 |
| 测试 | Vitest、RTL、Playwright，按需 MSW | 遵循仓库测试规范 |
| 可观测性 | OpenTelemetry 语义 + 供应商适配器 | 统一指标和追踪，避免锁定展示平台 |

实施时固定精确依赖版本，并使用迁移文件和锁文件控制升级。外部供应商的领域无关标识只保存在适配器字段中。

## 11. 集中待决策项

以下决策不改变本文的领域边界，但会影响实施计划中的配置文件、适配器和部署步骤。括号内为推荐默认值：

1. **模型与 API**：提供兼容 OpenAI 协议的服务地址、API Key 和模型 ID；候选模型必须实际通过工具调用、结构化输出、流式响应和中文质量契约测试，最终型号由 30 条样本确定。
2. **联网搜索**：选择能返回可靠链接、标题、摘要和发布时间的搜索服务（默认：独立搜索 API，不把模型内置搜索作为唯一来源）。
3. **用户名规则**：确认允许的字符和长度（默认：3–32 个 ASCII 字母、数字或下划线；显示保留输入大小写，唯一性比较使用规范化小写）。
4. **密码与找回**：确认最小长度和忘记密码替代路径（默认：12–128 个 Unicode 字符；MVP 不提供自助找回，由受控管理员流程重置测试账号）。
5. **任务执行器**：使用 Trigger.dev Cloud、自托管 Trigger.dev 或目标平台的等价持久任务能力（默认：MVP 使用 Trigger.dev Cloud，保留端口）。
6. **PostgreSQL 托管**：选择与部署区域、连接方式和备份要求匹配的服务（默认：托管 PostgreSQL，开发/测试使用本地实例）。
7. **部署平台与区域**：决定 Web、任务和数据库部署位置（默认：Node.js 兼容平台，数据与任务尽量同区）。
8. **产品分析与可观测性后端**：确定事件、指标和追踪的落点（默认：产品事件写入 PostgreSQL，OpenTelemetry 导出到一个监控后端）。
9. **链接解析范围**：是否在 MVP 验证前实施 M5（默认：不阻塞文本闭环，完成 M4 后按剩余时间决定）。
10. **交付约束**：团队人数、目标日期、月度模型/搜索预算和预计并发（默认：计划以依赖顺序表达，不承诺日历工期）。

这些决策应在对应适配器进入实现前确认。若暂不确认，实施计划按推荐默认值编写，并把替换点列为明确接口。

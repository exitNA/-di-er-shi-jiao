# 聊天优先的 Agent 长任务感知设计

## 目标

保持用户与客户经理的连续聊天体验。在客户经理处理单轮请求时，用户能看见本轮实际参与的 Agent、当前进度和安全的工作摘要，并可继续输入或终止任务。

## 交互模型

每一轮由一条用户消息和其后的客户经理回复构成。Agent 不作为独立聊天发言者。

- 已完成回复：客户经理正式回复下方显示紧凑摘要，例如“3 位 Agent 已参与 · 查看本轮工作过程”。
- 进行中回复：客户经理先显示“我正在协调团队核对信息”，随后显示本轮参与 Agent 的重叠头像组、步骤进度与“查看本轮工作过程”。
- 展开过程：在同一条客户经理回复内显示扁平时间线。每条记录包含 Agent 名称、用户可理解的工作摘要、状态、进度与可选的安全工具结果摘要。
- 完成：过程自动收束为摘要，客户经理的正式回答保持为该回复的主体。
- 用户输入：输入框始终固定在聊天区底部；任务运行时仍可输入，提交按钮切换为终止按钮。

## 信息与安全边界

- 参与者按业务 run 分组，历史轮次只显示该轮实际参与的 Agent。
- 时间线使用已经脱敏、适合用户阅读的摘要；不展示 UUID、原始事件 JSON、凭据、工具参数原文或模型思考原文。
- 工具详情只在事件提供安全输入/结果摘要时显示；缺少安全摘要时仅显示工具名称和状态。

## 布局

桌面端继续使用现有聊天列与报告列。长任务感知只发生在聊天列的客户经理回复内，不新增全局 Agent 看板、侧栏或控制台。

移动端沿用聊天/报告切换；过程摘要与时间线随客户经理消息自然流动。

## 验收条件

- 用户可清楚辨认连续的“用户 → 客户经理”对话，不会看到 Agent 作为聊天角色。
- 每轮过程只列出该轮的参与 Agent。
- 运行中的客户经理回复可实时更新参与者、摘要与进度。
- 已完成轮次默认紧凑，点击可查看该轮过程。
- 过程数据再长也只在消息内的可控区域展开，不影响固定输入框。
- 终止、错误、可恢复与完成状态具有文本提示，且不只依赖颜色。
